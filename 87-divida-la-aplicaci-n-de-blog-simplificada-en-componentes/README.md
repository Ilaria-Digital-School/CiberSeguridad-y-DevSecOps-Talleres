# Divida la aplicación de blog simplificada en componentes

RECORDATORIO TEÓRICO Descomponer una aplicación en componentes es el primer paso indispensable del modelado de amenazas. Un componente es una parte identificable del sistema que cumple una función concreta: una interfaz de usuario, un servidor de aplicación, una base de datos, un servicio de autenticación, una API externa, etc. El modelo mental clave consiste en imaginar la aplicación como un conjunto de "cajas" (procesos, almacenes de datos, entidades externas) conectadas por "flujos de datos" (peticiones HTTP, consultas SQL, llamadas API). Alrededor de estas cajas se dibujan las fronteras de confianza (trust boundaries): líneas que separan zonas con distintos niveles de confianza, por ejemplo entre el navegador del visitante (no confiable) y el servidor (confiable). Estas fronteras son precisamente donde suelen aparecer los riesgos que aprendió a mapear con OWASP. Un error frecuente en principiantes es confundir componentes con simples archivos de código, o bien crear una lista demasiado detallada que impide ver el conjunto. Otro error es olvidar los actores externos (usuarios, atacantes, servicios de terceros) y los almacenes de datos, que son objetivos clásicos en términos de confidencialidad, integridad y disponibilidad (CIA). Mini-ejemplo: en un blog, un componente sería "Base de datos de artículos" (almacén de datos), otro "Navegador del lector" (entidad externa), y entre ellos el "Servidor web" (proceso). El flujo "lectura de un artículo" cruza la frontera entre la zona pública de Internet y la zona interna del servidor.
